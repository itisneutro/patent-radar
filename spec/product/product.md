# Патентный радар — описание продукта

> **Статус: контрольная точка 1 (2026-10-07).** Готовы спецификации и кликабельный прототип интерфейса на заглушках. Поиск по корпусу и языковая модель на КТ1 не работают: выдача и пояснение в прототипе — заранее подготовленные демонстрационные данные (записи `DEMO-001` … `DEMO-003`).

## 1. Коротко

Патентный радар — инструмент первичного поиска аналогов. Пользователь описывает идею изобретения обычными словами. Система находит похожие патенты РФ в корпусе рефератов (собственная реализация BM25), а локальная языковая модель (через Ollama) кратко объясняет, чем каждый найденный патент похож на идею и чем отличается, со ссылками на номера патентов. Радар помогает сделать первый шаг; юридическим заключением его результат не является.

## 2. Пользователи

### 2.1. Изобретатель-одиночка

- **Кто.** Инженер, мастер или любитель-конструктор, который сам придумывает и делает устройства. Патентного образования нет; денег на патентного поверенного на ранней стадии обычно тоже нет.
- **Типичная ситуация.** Придумал, например, полив грядок, который включается, когда почва пересохла, и не включается перед дождём. Прежде чем тратить время и деньги на прототип и заявку, хочет понять, нет ли уже такого решения.
- **Что нужно.** Быстро увидеть близкие патенты и понять, чем они отличаются от его идеи; получить номера, чтобы прочитать документы целиком в реестре.
- **Чем помогает радар.** Принимает описание обычными словами и показывает похожие патенты РФ с коротким пояснением «чем похоже, чем отличается» и номерами. С такой выдачей проще решить, продолжать ли работу над идеей, и подготовиться к разговору с патентным поверенным.

### 2.2. Студент

- **Кто.** Студент технического вуза: курсовой проект, НИРС, выпускная работа, проект на конкурс.
- **Типичная ситуация.** Нужен раздел «Анализ существующих решений»: найти несколько патентов по теме и сравнить их со своим решением. Опыта работы с патентными базами нет.
- **Что нужно.** Стартовый список релевантных патентов, понятные формулировки сходств и отличий, номера для списка источников.
- **Чем помогает радар.** Даёт стартовый список и подсказку для сравнения. Дальше студент открывает каждый документ по номеру в открытом реестре ФИПС и формулирует выводы сам: пояснение радара — подсказка, а не готовый текст для отчёта.

### 2.3. Стартап

- **Кто.** Небольшая команда на ранней стадии, которая делает технический продукт (устройство, способ, систему) и готовит заявку в акселератор, на грант или встречу с инвестором.
- **Типичная ситуация.** Нужно быстро понять, насколько «занята» область, и найти близкие решения до заказа платного патентного поиска. До подачи заявки описание продукта конфиденциально, и отправлять его во внешние онлайн-сервисы команда не хочет.
- **Что нужно.** Быстрый обзор близких решений, аргументы для разговора с патентным поверенным, конфиденциальность запросов.
- **Чем помогает радар.** Работает на компьютере команды, запросы его не покидают. Можно перебрать несколько формулировок идеи, сузить выдачу фильтрами по году и МПК и передать найденные номера поверенному.

## 3. Проблема: почему искать аналоги трудно

1. **Юридический язык рефератов и формул.** Пример из демонстрационных данных: «…отличающаяся тем, что контроллер выполнен с возможностью открывать клапан зоны при снижении влажности почвы ниже нижнего порогового значения…». Суть приходится вычитывать из длинных фраз со служебными оборотами «содержащий», «выполненный», «отличающийся тем, что».
2. **Классификация МПК.** Патенты разложены по Международной патентной классификации — иерархии из разделов, классов, подклассов, групп и подгрупп (десятки тысяч рубрик). Чтобы искать по классу, нужно знать код, а одна идея часто попадает в разные разделы. В демонстрационных данных тема «полив по влажности почвы» встречается в подклассах A01G (садоводство, орошение), G01N (исследование материалов, в том числе измерение влажности) и H04W (беспроводная связь).
3. **Официальные поисковые системы требуют навыка.** Открытые реестры ФИПС удобны, когда номер документа уже известен. Чтобы искать по смыслу в профессиональных поисковых системах, нужно выбирать базы и поля, строить запросы с логическими операторами, знать термины и коды МПК — этому специально учат патентоведов.
4. **Слова пользователя не совпадают с терминами патентов.** Человек пишет «грядки на даче поливались сами», «почва пересохла», «обещают дождь», а в рефератах — «система автоматического полива», «при снижении влажности почвы ниже нижнего порогового значения», «вероятность осадков». Поиск по совпадению слов такие документы пропускает или ставит низко.

## 4. Ценность

**Описал идею своими словами → получил список похожих патентов РФ и краткое объяснение сходств и отличий со ссылками на номера.**

- **Быстро.** Один запрос обычным языком вместо составления поисковых выражений; первый ориентир — за минуты (целевой показатель — в разделе 8.2).
- **Бесплатно.** Открытые данные ФИПС, свободные компоненты, локальная модель; платных сервисов и подписок нет. Нужен компьютер, на котором запускается локальная модель: рекомендуемая `qwen2.5:7b` занимает около 4,7 ГБ, для слабых ноутбуков — `qwen2.5:3b`.
- **Локально.** Поиск и пояснение выполняются на компьютере пользователя; описание идеи не передаётся во внешние сервисы.
- **Проверяемо.** Абзац пояснения о каждом патенте начинается с его номера `[ID]` из выдачи; по номеру открывается карточка с рефератом, и любое утверждение можно сверить с источником.

## 5. Что делает продукт

**Вход:** описание идеи на русском языке (не меньше 3 слов и не больше 2000 символов) и необязательные фильтры: год публикации «с … по …» (1900–2100), префикс кода МПК (до 20 символов), количество результатов (5, 10 или 20; по умолчанию 10).

**Выход:**

- карточки похожих патентов по убыванию оценки BM25: номер, название, коды МПК, год публикации, оценка и полоса релевантности;
- карточка патента: позиция в выдаче и оценка BM25, номер, название, МПК, год публикации, реферат;
- пояснение: вводный абзац; по абзацу на каждый патент, реферат которого получила модель (первые 5 результатов выдачи), — абзац начинается со ссылки `[ID]`; в конце — фраза «Это первичный поиск аналогов, а не юридическое заключение о новизне или патентоспособности.» (её добавляет API, а не модель).

**Целевая схема (КТ2):** запрос → предобработка (нижний регистр, токенизация, лемматизация pymorphy3, патентные стоп-слова) → BM25 по рефератам и названиям → фильтры по году и МПК → первые `top_k` результатов → рефераты первых пяти — в контекст локальной LLM → пояснение. Подробности поиска — в [`spec/tech/rag.md`](../tech/rag.md), архитектура и контракт API — в [`spec/tech/architecture.md`](../tech/architecture.md).

**Что из этого работает на КТ1:**

| Шаг | Цель (КТ2) | Прототип КТ1 |
|---|---|---|
| Проверка ввода | не меньше 3 слов, не больше 2000 символов, годы 1900–2100, префикс МПК до 20 символов | работает в интерфейсе и в заглушке API |
| Поиск | собственный BM25 по корпусу ~200 рефератов | заглушка: если в запросе есть слово на тему полива и влажности почвы, возвращаются 3 демонстрационные записи в фиксированном порядке, иначе выдача пуста |
| Фильтры и количество результатов | год, префикс МПК, `top_k` | работают на демонстрационных записях |
| Пояснение | локальная LLM через Ollama по рефератам первых 5 результатов | заранее составленный текст, модель не вызывается |
| Интерфейс | экран запроса, выдача, карточка патента, пустая выдача, ошибки | кликабельный прототип на моке [`frontend/src/mock/search.json`](../../frontend/src/mock/search.json) |

Пример на демонстрационных данных: запрос «Хочу, чтобы грядки на даче поливались сами: датчик в земле замечает, что почва пересохла, и включает воду, а если обещают дождь, полив не включается.» → выдача `DEMO-002`, `DEMO-001`, `DEMO-003` и пояснение, например: «[DEMO-002] Ближе всего к вашей идее: полив зависит от влажности почвы и откладывается, если ожидаются осадки. Отличие: …». Записи `DEMO-xxx` — демонстрационные данные, а не реальные патенты.

## 6. Границы продукта

- **Только рефераты патентов РФ.** Корпус — рефераты изобретений РФ из открытых реестров ФИПС, собранные вручную. Полные тексты (описание, формула) и зарубежные патенты в корпус не входят, полезные модели и промышленные образцы — тоже. Следствие: аналог, который есть только за рубежом или виден только из формулы и описания, радар не найдёт. Пустая выдача не означает, что аналогов нет.
- **Не юридическое заключение.** Радар не оценивает новизну и патентоспособность, не заменяет патентного поверенного и официальный патентный поиск. Каждое пояснение заканчивается фразой «Это первичный поиск аналогов, а не юридическое заключение о новизне или патентоспособности.» Та же фраза стоит в подвале интерфейса на всех экранах.
- **Данные не уходят в облако.** Языковая модель работает локально через Ollama, запросы не передаются третьим лицам. Корпус, индекс, бэкенд и интерфейс работают на компьютере пользователя; интерфейс не подключает внешние скрипты, аналитику и шрифты из интернета (шрифты — из npm-пакетов). Режим `LLM_PROVIDER=openai_compatible` допустим только с сервером на том же компьютере (LM Studio, llama.cpp server, vLLM): если сервер удалённый, запрос уходит на него, а это нарушает принцип.

## 7. Что не входит в MVP

- Полные тексты патентов, полезные модели, промышленные образцы, зарубежные патентные базы.
- Автоматический сбор корпуса (парсер реестров ФИПС): рефераты собираются вручную, формат записи — [`data/sample/README.md`](../../data/sample/README.md).
- Векторный и гибридный поиск, эмбеддинги, переранжирование моделью: в проекте только собственный BM25.
- Оценка новизны и патентоспособности, «процент сходства», советы по составлению формулы.
- Ссылка из карточки на документ в реестре ФИПС: в контракте API такого поля нет, документ ищется в реестре по номеру вручную.
- Учётные записи, история запросов, экспорт отчёта (PDF, DOCX), совместная работа.
- Облачное развёртывание и облачные LLM-API.
- Запросы на других языках: корпус и пояснения — на русском.

## 8. Критерии успеха

### 8.1. Качество поиска (benchmark, КТ2)

Метрики и порядок расчёта описаны в [`spec/tech/rag.md`](../tech/rag.md). Benchmark — 24 запроса, написанных своими словами: по 3 на каждую из 8 тем корпуса, у каждого не меньше 3 релевантных документов. Две трети запросов (dev) используются для подбора параметров, треть (test) — для итоговой проверки.

| Метрика | Что показывает | Целевой ориентир (гипотеза) |
|---|---|---|
| Recall@5 | долю релевантных документов запроса, которые попали в первые 5 результатов: \|Rel ∩ Top5\| / \|Rel\| (именно эти 5 рефератов уходят в контекст LLM); главная метрика выбора конфигурации | ≥ 0.5 |
| Recall@10 | полноту выдачи при `top_k = 10` | ≥ 0.7 |
| MRR (MRR@10) | насколько высоко стоит первый релевантный документ | ≥ 0.6 |

**Ориентиры — гипотеза до первых экспериментов**, а не измеренные значения: это стартовая планка для лексического поиска по ~200 рефератам. На КТ2 после прогона baseline (конфигурация A1 в `spec/tech/rag.md`) ориентиры пересматриваются. С ориентирами сравниваются только измеренные значения на test-части; таблицы подбора на dev приводятся отдельно и для сравнения с ориентирами не используются. Отдельное условие: выбранная конфигурация на test-части не хуже baseline по Recall@5.

### 8.2. Пользовательские критерии (КТ2–КТ3)

Проверяются на основном сценарии из [`spec/product/scenarios.md`](scenarios.md) с 3–5 участниками вне команды (например, сокурсниками): каждый описывает своими словами идею на одну из тем корпуса.

| Критерий | Как проверяем | Ориентир (гипотеза) |
|---|---|---|
| Время до первого полезного аналога | от открытия «Экрана запроса» до открытия «Карточки патента», которую участник назвал похожим решением; переформулировки запроса входят во время | медиана ≤ 5 минут |
| Понятность пояснений | по каждому абзацу о патенте участник отвечает, понятно ли, чем патент похож на идею и чем отличается («да», «частично», «нет»); команда сверяет абзац с рефератом: нет ли фактов, которых в реферате нет | ≥ 80% ответов «да»; каждый абзац с фактами не из реферата разбирается и исправляется правкой промпта |
| Ссылки на номера | автоматически: каждый абзац о патенте начинается с `[ID]`, все `[ID]` есть в выдаче, последний абзац — дисклеймер | 100% ответов — обязательное требование, проверяется тестами API |

На КТ1 пользовательские критерии не измеряются: поиск не работает, пояснение заготовлено заранее. Заглушка показывает только формат ответа (ссылки `[ID]`, дисклеймер), его проверяют тесты API.

## 10. Риски и как их снижаем

| Риск | Чем грозит | Как снижаем |
|---|---|---|
| Слова пользователя не совпадают с терминами рефератов | BM25 — лексический поиск: аналоги, описанные другими словами, не находятся или стоят низко | лемматизация pymorphy3 объединяет формы слова; патентные стоп-слова убирают служебные обороты; подсказка в интерфейсе просит описать, что это, из чего состоит и как работает; benchmark из запросов своими словами измеряет разрыв; эксперименты с предобработкой и параметрами BM25 |
| Маленький корпус, собранный вручную | аналога нет в корпусе — пустая или слабая выдача, а пользователь решает, что аналогов нет вообще | границы продукта описаны явно; дисклеймер — в конце каждого ответа с результатами и в подвале интерфейса на всех экранах, включая «Ничего не найдено»; текст пустой выдачи предлагает переформулировать запрос и ослабить фильтры; на КТ2, когда темы корпуса будут выбраны, их список появится в `README.md` и на «Экране запроса» |
| Ручной сбор ~200 рефератов трудоёмок, в записях возможны ошибки (МПК, год) | срыв сроков КТ2, неверная работа фильтров | темы распределены между участниками; единый формат записи в `data/sample/README.md`; МПК и год переносятся из полей (51) и (45) документа в реестре; второй участник выборочно сверяет записи |
| Модель выдумывает факты или номера | пользователь делает неверные выводы | в контексте только рефераты первых 5 результатов; промпт запрещает выдумывать и ссылаться на номера вне выдачи; API убирает ссылки на номера не из выдачи; температура 0.2; ручная проверка пояснений на запросах benchmark |
| Модель делает юридические выводы («не обладает новизной») | пояснение принимают за заключение | запрет в промпте; дисклеймер добавляет API, а не модель; тот же дисклеймер — в подвале интерфейса на всех экранах; ручная проверка |
| Локальная модель работает медленно или не запущена | долгое ожидание или ответ без пояснения | модель поменьше (`qwen2.5:3b`) для слабых ноутбуков; не больше 5 рефератов в контексте; тайм-аут `LLM_TIMEOUT_SECONDS`; при ошибке модели выдача возвращается без пояснения, а не ошибкой сервиса |
| Параметры BM25 подгоняются под маленький benchmark | хорошие цифры на benchmark, слабый поиск на новых запросах | разделение запросов на dev и test; запросы пишет участник, который не собирал эту тему; релевантность подтверждают двое |
| Запросы уходят на внешний сервер после смены провайдера LLM | нарушается принцип «данные не уходят в облако» | по умолчанию `LLM_PROVIDER=ollama`; предупреждение в `.env.example` и `spec/tech/architecture.md`; в продукте — только локальные серверы |
| Интерфейс, API и документация расходятся (трое участников работают параллельно) | прототип и бэкенд ведут себя по-разному | единый контракт API в `spec/tech/architecture.md`; мок `frontend/src/mock/search.json` строго по контракту; тесты сверяют ответ API и мок с контрактом; сценарии с критериями приёмки |
