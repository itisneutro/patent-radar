## 1. Назначение и место в RAG-конвейере

«Патентный радар» — RAG-приложение. Retrieval — собственный BM25 по корпусу рефератов патентов РФ; generation — локальная LLM через Ollama, которая коротко объясняет, чем найденные патенты похожи на идею пользователя и чем отличаются. Этот документ описывает retrieval: как текст превращается в термины, как устроены индекс и ранжирование, как выбираем настройки и оцениваем качество. Схема всего конвейера, контракт API и выбор LLM — в [spec/tech/architecture.md](architecture.md).

Путь запроса (КТ2):

1. `POST /search` получает `query` и фильтры `top_k`, `year_from`, `year_to`, `ipc`.
2. Запрос проходит ту же предобработку, что и документы (раздел 4).
3. BM25 (раздел 6) оценивает документы, в которых есть хотя бы один термин запроса. Порядок — по убыванию score, при равенстве — по `id`.
4. API применяет фильтры по году и МПК и порог `MIN_SCORE` (раздел 7), затем обрезает выдачу до `top_k`.
5. Первые `MAX_CONTEXT_DOCS = 5` результатов подставляются в промпт (`app/llm/prompts.py`), ответ модели становится полем `answer`. Если выдача пуста, `answer` — фиксированный текст «ничего не найдено», LLM не вызывается.

| Модуль | Что делает | Раздел |
|---|---|---|
| `app/search/preprocess.py` | нормализация, коды МПК, токенизация, лемматизация, стоп-слова | 4 |
| `app/search/index.py` | инвертированный индекс | 5 |
| `app/search/bm25.py` | ранжирование BM25 | 6, 7 |
| `app/llm/prompts.py` | промпт: первые 5 рефератов и запрос | 1, 9 |
| `benchmark/experiments.py` | тетрадка marimo: проверка benchmark, метрики, эксперименты | 8–10 |

## 2. Единица поиска: название + реферат

Документ для поиска = **название** (INID 54) + **реферат** (INID 57). Коды МПК (51) и год публикации (45) — метаданные для фильтров и показа; в текст документа они не входят (кроме опыта C2).

Почему не весь текст патента:

- Реферат короткий (обычно 100–250 слов) и единообразен по форме: суть изобретения и технический результат. Именно это пользователь сравнивает со своей идеей.
- Рефераты можно вручную собрать из открытых реестров ФИПС (инструкция — в `data/sample/README.md`).
- Полное описание и формула длинные, полны юридических оборотов и сильно различаются по длине. Длинный документ набирает совпадения со случайными словами запроса, а нормировка длины в BM25 (параметр b) рассчитана на документы сопоставимой длины.
- В контекст локальной LLM идут 5 документов целиком: рефераты в него помещаются, полные описания — нет.

Название добавляем к реферату: оно короткое и состоит из главных терминов («Беспроводной датчик влажности почвы с автономным питанием»).

## 3. Корпус: формат записи и источники

Корпус — файл JSONL в UTF-8, одна запись патента на строку. Полное описание полей, правила нормализации и пошаговая инструкция ручного сбора рефератов из открытых реестров ФИПС — в [data/sample/README.md](../../data/sample/README.md).

| Поле | Тип | Источник в документе ФИПС (код INID) |
|---|---|---|
| `id` | string | (19) + (11) + (13): `RU<номер><код вида>`, например `RU<7 цифр>C1`; у демо-записей `DEMO-001` |
| `title` | string | (54) название |
| `abstract` | string | (57) реферат, одной строкой |
| `ipc` | string[] | (51) коды МПК вида `A01G 25/16`, без версии `(2006.01)` |
| `year` | integer | год из (45) — даты публикации |
| `source` | string | URL страницы документа в открытом реестре ФИПС или `"демонстрационные данные"` |

- `data/sample/patents.jsonl` — 3 записи `DEMO-001`…`DEMO-003` (полив и датчики влажности почвы). Это **демонстрационные данные**, составленные вручную для прототипа: не реальные патенты, `DEMO-…` — не номера патентов.
- `data/corpus/patents.jsonl` — реальный корпус (~200 рефератов, раздел 10), появится к КТ2.

## 4. Предобработка

Одна функция `preprocess(text, config)` обрабатывает и документы, и запросы: если их обработать по-разному, термины не совпадут. Токены документа = `preprocess(title) + preprocess(abstract)`.

Порядок шагов важен:

| № | Шаг | Функция | Пример |
|---|---|---|---|
| 1 | Unicode NFC и нижний регистр | `normalize` | «Хочу, чтобы грядки…» → «хочу, чтобы грядки…» |
| 2 | Коды МПК → один токен, до токенизации | `extract_ipc_codes` | «A01G 25/16 (2006.01)» → `a01g25/16` |
| 3 | Токенизация с сохранением дефисов | `tokenize` | «кремний-органическое», «wi-fi» — по одному токену |
| 4 | Лемматизация pymorphy3 | `lemmatize` | «поливались» → `поливаться` |
| 5 | «ё» → «е» после лемматизации | `fold_yo` | «причём» → `причем` |
| 6 | Удаление стоп-слов | `remove_stopwords` | `отличаться`, `тем`, `что` удаляются |

Флаги — `PreprocessConfig(lemmatize, general_stopwords, patent_stopwords)`, по умолчанию все `True` (полный конвейер, опыт A5). Шаги 1–3 и 5 выполняются всегда; без лемматизации шаг 5 идёт сразу после токенизации. Коды МПК добавляются в конец списка токенов.

Все леммы и трассировки в этом разделе — реальный вывод pymorphy3 2.0.6 (словарь pymorphy3-dicts-ru 2.4.417150.4580142) на Python 3.12, полученный при подготовке КТ1.

### 4.1. NFC и нижний регистр

`unicodedata.normalize("NFC", text).lower()`. Текст, скопированный с веб-страниц и из PDF, может содержать «разложенные» буквы: «й» = «и» + U+0306, «ё» = «е» + U+0308. Комбинирующий знак не считается буквой, и слово рвётся. Проверка: строка «Беспроводной датчик, ёмкостный элемент» в разложенной форме (NFD) без NFC токенизируется в `беспроводнои`, `датчик`, `е`, `мкостныи`, `элемент`, а после NFC — в `беспроводной`, `датчик`, `ёмкостный`, `элемент`.

### 4.2. Коды МПК

Код МПК (`A01G 25/16`) содержит пробел и косую черту, и обычная токенизация разбила бы его на `a01g`, `25`, `16`. Поэтому коды извлекаются регулярным выражением **до** токенизации слов: из текста код удаляется (заменяется пробелом), а в список токенов попадает одним токеном без пробела — `a01g25/16`.

Выражение применяется к тексту в нижнем регистре:

```python
IPC_RE = re.compile(
    r"\b([a-hавсен])(\d{2})([a-zавсенкмортх])\s*(\d{1,4})/(\d{2,6})\b"
    r"(?:\s*\(\d{4}\.\d{2}\))?"
)
LOOKALIKES = str.maketrans("авсенкмортх", "abcehkmoptx")
# токен = (раздел + класс + подкласс).translate(LOOKALIKES) + группа + "/" + подгруппа
```

- раздел — буква A–H, класс — 2 цифры, подкласс — буква, основная группа — 1–4 цифры, подгруппа — 2–6 цифр;
- на месте букв допускаются кириллические буквы-двойники А, В, С, Е, Н, К, М, О, Р, Т, Х (после нижнего регистра — «авсенкмортх»): их часто набирают вместо латинских, они заменяются латиницей;
- версия редакции МПК в скобках, например `(2006.01)`, отбрасывается вместе с кодом;
- коды не лемматизируются и не сверяются со стоп-словами.

Проверка на тестовых строках:

| Вход | Коды | Остальные токены |
|---|---|---|
| «Датчик по МПК G01N 33/24 и A01G 25/16 (2006.01), см. также G05B19/042» | `g01n33/24`, `a01g25/16`, `g05b19/042` | `датчик`, `по`, `мпк`, `и`, `см`, `также` |
| «Аналоги в А01G 25/16 и Н04W 4/38» (А и Н — кириллические) | `a01g25/16`, `h04w4/38` | `аналоги`, `в`, `и` |

В рефератах коды встречаются редко. Шаг нужен для запросов, в которые пользователь вставил код, и для опыта C2.

### 4.3. Токенизация

```python
WORD_RE = re.compile(r"[^\W_]+(?:-[^\W_]+)*")
tokens = WORD_RE.findall(text)
```

`[^\W_]` — буква или цифра любого алфавита (`\w` без подчёркивания). Класс символов тот же, что в проверке запроса в API («не меньше 3 слов»), но там дефис разделяет слова («Wi-Fi» — два слова), а токенизатор сохраняет слово с дефисом одним токеном: «кремний-органическое», «wi-fi», «интернет-магазин». Знаки препинания, тире «—», кавычки и скобки — разделители.

Пример: «Покрытие кремний-органическое, связь по Wi-Fi, 12 часов, 0,5 л, т. е. «умный» полив — проект» → `покрытие`, `кремний-органическое`, `связь`, `по`, `wi-fi`, `12`, `часов`, `0`, `5`, `л`, `т`, `е`, `умный`, `полив`, `проект`. Числа остаются токенами; десятичная дробь распадается на части — для поиска по рефератам это допустимо.

### 4.4. Лемматизация pymorphy3

Правило: `MorphAnalyzer().parse(token)[0].normal_form` для токенов из кириллических букв и дефисов (`re.fullmatch(r"[а-яё]+(?:-[а-яё]+)*", token)`). Коды МПК, числа, латиница и смешанные токены не лемматизируются.

Зачем. Русский язык сильно флективный: без лемматизации «почва», «почвы», «почве» — три разных термина, и запрос «почва пересохла» не совпадёт с «влажности почвы». На демо-данных основной демо-запрос (раздел 4.7) после полного конвейера делит с DEMO-001 три леммы — `вода`, `датчик`, `почва`, а без лемматизации (опыт A3) — ни одного термина.

**Почему pymorphy3.**

- Словарный морфологический анализатор (словарь OpenCorpora): возвращает настоящую начальную форму, а не обрубок: «отличающийся» → `отличаться`, «воду» → `вода`.
- Понимает слова через дефис («кремний-органическим» → `кремний-органический`, «интернет-магазина» → `интернет-магазин`) и «е» на месте «ё» («емкостные» и «ёмкостные» → `ёмкостный`).
- Лёгкий: пакет на Python и пакет словаря, без нейросетевых моделей; разбирает слово без контекста — для BM25 этого достаточно.
- Поддерживается: версия 2.0.6 вышла в октябре 2025 года, на PyPI заявлены Python 3.9–3.13. Методичка разрешает его явно.

**Почему не стемминг Snowball.** Стеммер отрезает окончания по правилам, без словаря, — грубо и с путаницей основ. Вывод `snowballstemmer` 3.1.1 (русский): «полив», «полить», «пол», «поле» → `пол` (четыре разных слова слились в одну основу); «вода», «водить» → `вод`. При этом формы одного слова расходятся: «поливом» → `полив`, а «поливать», «поливались» → `полива`; «содержащий» → `содержа`, «содержит» → `содерж`; «выполненный» → `выполнен`, «выполнен» → `выполн`. Основы — не слова, поэтому стоп-список в виде основ труднее составить и проверить.

**Почему не pymorphy2.** Не поддерживается — последний выпуск 0.9.1 вышел в сентябре 2020 года — и не работает на Python 3.11+. Проверка на Python 3.12: `MorphAnalyzer()` падает с `ModuleNotFoundError: No module named 'pkg_resources'` (в актуальном setuptools 84.0.0 этого модуля нет), а со старым setuptools — с `AttributeError: module 'inspect' has no attribute 'getargspec'` (функция удалена в Python 3.11). pymorphy3 — продолжение pymorphy2 с тем же интерфейсом (`MorphAnalyzer`, `parse`, `normal_form`, `lexeme`).

**Почему не Natasha, spaCy, Stanza.** Это полные NLP-конвейеры (сегментация, морфологическая разметка, синтаксис) на нейросетевых моделях; лемма в них — побочный продукт разбора предложения. Они тяжелее (модели, крупные зависимости) и медленнее, а для BM25 избыточны: нужна только лемма отдельного слова.

**Неоднозначность разбора: берём `parse()[0]`.** `parse()` возвращает гипотезы разбора, отсортированные по `score` — оценке вероятности разбора по размеченному корпусу OpenCorpora; контекст не учитывается. Берём первую гипотезу. Плюс — детерминированность: одна и та же словоформа всегда даёт одну лемму и в документе, и в запросе. Минус — неоднозначные слова (реальный вывод):

- «установленный» → `установленный` (прилагательное ADJF, score 0,25; разборы-причастия от «установить» с тем же score стоят ниже), а «установлен» → `установить`. Поэтому в патентном стоп-списке обе леммы. Так же «связанный» → `связанный`, а не `связать`.
- «полив» (именительный и винительный падеж) → `полить`: первым идёт разбор-деепричастие GRND со score 0,4, разборы-существительные — по 0,2. А «полива», «поливом», «поливе» → `полив`. Одно существительное получает две леммы; в основном демо-запросе «полив не включается» даёт `полить`. Это известная потеря, варианты исправления — в разделе 11.
- Служебные слова: «тем» → `тем` (союз), «этом» → `это`, «её» → `её` (притяжательное местоимение), «все» → `всё`. Поэтому эти формы есть в общем стоп-списке.

Причастия приводятся к инфинитиву (PRTF → INFN): «отличающийся» → `отличаться`, «выполненный» → `выполнить`. Лемматизация объединяет словоизменение, но не словообразование: «поливались» → `поливаться`, но `поливаться` и `полив` — разные термины; «влажности» → `влажность`, а «влаги» → `влага`.

**«ё» → «е» после лемматизации.** pymorphy3 понимает «е» на месте «ё», но нормальные формы возвращает с «ё»: «причем» → `причём`, «емкостные» → `ёмкостный`. Поэтому замена идёт после лемматизации: «причём» и «причем» дают один токен `причем`. Стоп-списки записаны через «е».

**Кэширование.**

- Один `MorphAnalyzer` на процесс: при создании он загружает словари, поэтому создаётся лениво при первом вызове и переиспользуется. `import pymorphy3` — внутри функции, чтобы пакет `app.search` импортировался без внешних зависимостей.
- Лемма отдельного токена кэшируется `functools.lru_cache`: слова в рефератах повторяются, и каждая уникальная словоформа разбирается один раз. Размер кэша ограничен числом уникальных словоформ корпуса и запросов.

### 4.5. Стоп-слова

Списки собственные (не из внешних библиотек), хранятся в `app/search/preprocess.py` в форме лемм, через «е». В коде они записаны ровно так, как ниже.

**Общие** (`GENERAL_STOPWORDS`, 78 лемм) — служебные слова русского языка:

```text
предлоги: без, в, для, до, за, из, к, между, на, над, о, около, от, перед, по, под, после, при, про, с, у, через
союзы: а, если, и, или, как, когда, либо, но, однако, так, также, тем, то, тоже, чем, что, чтобы
частицы: бы, вот, даже, еще, же, именно, ли, лишь, не, ни, только, уже
местоимения: ваш, весь, все, вы, ее, каждый, какой, который, кто, мой, мы, наш, он, она, они, оно, свой, себя, такой, твой, тот, ты, это, этот, я
вспомогательные глаголы: быть, мочь
```

- «во», «со», «ко», «об», «обо» отдельно не нужны: pymorphy3 приводит их к `в`, `с`, `к`, `о`, а `lexeme` этих лемм их содержит.
- «его» → `он`, «их» → `они`, а «её» pymorphy3 разбирает как притяжательное `её`, которое после шага 5 становится `ее`; «ещё» → `еще`.
- `быть` и `мочь` — из оборота «может быть использовано», который есть почти в каждом реферате.

**Патентные** (`PATENT_STOPWORDS`, 23 леммы, базовый список):

```text
отличаться, содержать, выполнить, характеризоваться, снабдить, установить, установленный, расположить, обеспечивать, обеспечить, предназначить, включать, относиться, являться, позволять, заключаться, осуществляться, осуществлять, изобретение, технический, результат, причем, возможность
```

Почему «отличающийся», «содержащий», «выполненный» и подобные — стоп-слова. Реферат обычно пересказывает формулу изобретения и повторяет её служебные обороты: «Изобретение относится к …», «Система …, содержащая …, отличающаяся тем, что … выполнен с возможностью …», «Технический результат — …». Эти обороты есть почти в каждом реферате и ничего не говорят о предмете изобретения, то есть не различают документы. IDF снижает их вес, но не до нуля (в варианте Lucene IDF > 0, раздел 6); кроме того, они удлиняют документы и дают совпадения с запросами вроде «устройство содержит датчик». Поэтому базовый список удаляет их явно.

«способ», «устройство», «система» в базовый список не входят: они говорят о типе изобретения, а их вес и так снижает IDF. Расширенный список с ними — отдельный опыт C3.

Побочный эффект (реальный вывод): в основном демо-запросе «…и включает воду…» глагол «включает» → `включать` удаляется как патентное стоп-слово, хотя здесь он значимый; то же в примере Q-002 из `benchmark/queries.example.jsonl` («когда включать воду»). Вклад патентного списка измеряется сравнением A4 и A5.

Словоформа → лемма (`parse()[0]`, pymorphy3 2.0.6):

## 6. BM25

Вариант с неотрицательным IDF, как в Lucene (`app/search/bm25.py`, класс `BM25`):

$$
\mathrm{IDF}(t) = \ln\left(1 + \frac{N - n_t + 0.5}{n_t + 0.5}\right)
$$

$$
\mathrm{score}(D, Q) = \sum_{t \in Q} \mathrm{IDF}(t) \cdot \frac{\mathrm{tf}(t, D) \cdot (k_1 + 1)}{\mathrm{tf}(t, D) + k_1 \cdot \left(1 - b + b \cdot \frac{|D|}{\mathrm{avgdl}}\right)}
$$

Плоская запись:

```text
IDF(t)      = ln(1 + (N − n_t + 0.5) / (n_t + 0.5))
score(D, Q) = Σ_{t ∈ Q} IDF(t) · tf(t, D) · (k1 + 1) / (tf(t, D) + k1 · (1 − b + b · |D| / avgdl))
```

- N — число документов; n_t — число документов, где есть термин t; tf(t, D) — сколько раз t встречается в D; |D| — длина D в токенах после предобработки; avgdl — средняя длина документа.
- Q — **множество** терминов запроса: повтор слова в запросе не увеличивает score.
- По умолчанию **k1 = 1.2, b = 0.75** — классические значения, они же по умолчанию в Lucene.
- Документ без общих с запросом терминов получает score = 0 и в выдачу не попадает.
- Порядок — по убыванию score, при равенстве — по `id`. Округление до 2 знаков — в API; score сравним только внутри одной выдачи.

**Почему IDF с «1 +».** В классической формуле `ln((N − n_t + 0.5) / (n_t + 0.5))` термин, который встречается больше чем в половине документов, получает отрицательный вес, и документ с этим термином проигрывает документу без него. В демо-корпусе (N = 3) лемма `почва` есть во всех трёх рефератах: классический IDF = ln(0,5 / 3,5) ≈ −1,95, вариант Lucene = ln(1 + 0,5 / 3,5) ≈ 0,13. Для термина из двух документов — −0,51 против 0,47, из одного — 0,51 против 0,98.

**k1 — насыщение частоты термина.** При |D| = avgdl вклад термина равен IDF · tf · (k1 + 1) / (tf + k1). При k1 = 1.2 одно вхождение даёт 1,0 · IDF, два — 1,375 · IDF, три — 1,571 · IDF, предел — 2,2 · IDF. Каждое следующее вхождение добавляет меньше предыдущего, и один термин, повторённый много раз, не перевешивает несколько разных совпавших терминов. При k1 = 0 учитывается только наличие термина; чем больше k1, тем ближе рост к линейному по tf.

**b — нормировка длины.** Множитель 1 − b + b · |D| / avgdl: при b = 0 длина не учитывается, при b = 1 tf нормируется на относительную длину полностью. Длинный документ содержит больше слов и чаще совпадает с запросом случайно — b это компенсирует.

**Почему у рефератов эффект b может быть меньше.** При |D| = avgdl множитель равен 1 при любом b: b действует только через разброс длин. Рефераты близки по длине (обычно 100–250 слов), поэтому |D| / avgdl ≈ 1. Например, при |D| = 1,2 · avgdl множитель равен 1,06 при b = 0.3 и 1,15 при b = 0.75 — различие небольшое; у полных описаний, длины которых сильно различаются, оно было бы заметнее. В демо-корпусе длины после полного конвейера — 61, 64 и 55 токенов (|D| / avgdl от 0,92 до 1,07), но три записи — не статистика: разброс длин реального корпуса покажем в тетрадке. По той же причине мал и tf: в демо-рефератах термин встречается от 1 до 6 раз, то есть k1 работает на начальном участке кривой насыщения.

## 7. Порог «ничего не найдено» (MIN_SCORE)

- Документы без общих терминов имеют score = 0 и в выдачу не попадают никогда.
- Этого мало: посторонний запрос может совпасть с документом случайно, по одному слову. Реальный пример: запрос `no_match` про складной зонт после предобработки делит с DEMO-002 лемму `погода` («прогноза погоды»), поэтому его score > 0, хотя документ не по теме.
- Поэтому в выдачу попадают только документы со score ≥ `MIN_SCORE`. Если после фильтров и порога ничего не осталось, `results` = [], `answer` = NO_RESULTS_ANSWER («Похожих патентов в корпусе не найдено. …»), LLM не вызывается.
- Подбор на КТ2: для запросов benchmark (dev) и набора заведомо посторонних запросов (в духе `no_match`) строим распределение score первого результата и выбираем порог, который отсекает посторонние запросы и не выбрасывает релевантные документы из первых 5 у запросов benchmark; проверяем на test. До подбора действует только условие score > 0.
- Score BM25 зависит от длины запроса и IDF его терминов, поэтому абсолютный порог груб. Если он не разделит запросы, попробуем относительный: score / (Σ_{t ∈ Q} IDF(t) · (k1 + 1)) — долю от верхней границы score этого запроса.
- На КТ1 score в заглушке — фиксированные демонстрационные значения, а не результат BM25.

### 8.4. Как выбираем победителя

## 9. Метрики

Rel_q — релевантные документы запроса q из benchmark, Top_k(q) — первые k id выдачи, Q — множество запросов (dev или test).

$$
\text{Recall@}k(q) = \frac{|\mathrm{Rel}_q \cap \mathrm{Top}_k(q)|}{|\mathrm{Rel}_q|}
$$

$$
\text{Recall@}k = \frac{1}{|Q|} \sum_{q \in Q} \text{Recall@}k(q)
$$

$$
\mathrm{MRR} = \frac{1}{|Q|} \sum_{q \in Q} \frac{1}{\mathrm{rank}_q}
$$

rank_q — позиция первого релевантного документа в первых 10 результатах; если в первых 10 его нет, 1 / rank_q = 0 (MRR@10).

Плоская запись:

```text
Recall@k(q) = |Rel_q ∩ Top_k(q)| / |Rel_q|
Recall@k    = (1 / |Q|) · Σ_{q ∈ Q} Recall@k(q)
MRR         = (1 / |Q|) · Σ_{q ∈ Q} 1 / rank_q,   1 / rank_q = 0, если в первых 10 нет релевантных
```

Если у запроса больше 5 релевантных, Recall@5 не может достичь 1. Это нормально: конфигурации сравниваются на одних и тех же запросах.

Пример расчёта — **иллюстрация, не результат**: выдуманные id D1…D12, к корпусу отношения не имеют. Тот же пример проверяет функции метрик в тетрадке.

| Запрос | Релевантные | Выдача, первые 10 | Recall@5 | Recall@10 | 1 / rank |
|---|---|---|---|---|---|
| T1 | D1, D4, D7 | D3, **D1**, D5, **D7**, D9, D2, **D4**, D8, D6, D10 | 2/3 ≈ 0,667 | 3/3 = 1 | 1/2 = 0,5 |
| T2 | D2, D5, D6 | D8, D9, D3, D1, D4, D7, D10, **D2**, D11, D12 | 0/3 = 0 | 1/3 ≈ 0,333 | 1/8 = 0,125 |
| Среднее | | | 0,333 | 0,667 | MRR = 0,3125 |

Почему так:

- **Recall@5 — главная метрика выбора.** В контекст LLM попадают первые 5 рефератов (`MAX_CONTEXT_DOCS = 5`): релевантный патент ниже пятого места модель не увидит и не объяснит.
- При равном Recall@5 решает **MRR**: насколько высоко стоит первый релевантный патент — его пользователь видит первым.
- **Recall@10** — полнота карточек результатов (по умолчанию `top_k = 10`).

## 10. План формирования benchmark

### 10.1. Корпус

~200 рефератов: 8 тем × ~25. Тема = подкласс МПК; все 8 подклассов — из разных разделов МПК (A–H), чтобы корпус покрывал разные области техники. Внутри темы собираем 3 группы близких патентов по 8–9 рефератов — тогда у каждого из трёх запросов темы найдётся не меньше 3 релевантных.

Предварительный список тем и распределение работы (утверждаем вместе до начала сбора; при замене темы берём другой подкласс того же раздела и правим эту таблицу и `data/sample/README.md`):

| Тема | Подкласс МПК | Область | Собирает рефераты | Пишет запросы |
|---|---|---|---|---|
| 1 | A01G | садоводство, выращивание растений, полив | Бобур | Коля |
| 2 | B62K | велосипеды и самокаты | Бобур | Коля |
| 3 | C02F | очистка воды и сточных вод | Бобур | Коля |
| 4 | D06F | стирка, сушка и глажение белья | Коля | Ника |
| 5 | E06B | двери, окна, жалюзи, ворота | Коля | Ника |
| 6 | F25D | холодильники и морозильные камеры | Коля | Ника |
| 7 | G01N | исследование и анализ материалов, датчики их свойств | Ника | Бобур |
| 8 | H02J | электропитание, зарядка аккумуляторов | Ника | Бобур |

Итого: Бобур собирает 3 темы и пишет 6 запросов, Коля — 3 темы и 9 запросов, Ника — 2 темы и 9 запросов. Бобур объединяет корпус и проверяет формат.

### 10.2. Запросы

- 24 запроса, по 3 на тему.
- Запрос пишет участник, который эту тему **не** собирал (таблица выше), своими словами, как написал бы пользователь: 1–3 предложения, не меньше 3 слов, без копирования терминов из рефератов. Автор опирается на название группы патентов («полив по датчику влажности»), а не на тексты рефератов.
- У каждого запроса не меньше 3 релевантных документов.

### 10.3. Разметка релевантности

- Релевантный документ — патент, который пользователь с этой идеей должен увидеть как аналог: то же назначение и сходный способ решения.
- Двойная проверка: автор запроса и собиравший тему независимо отмечают релевантные рефераты темы (и замеченные в других темах). В benchmark идут документы, отмеченные обоими; спорные случаи решаем обсуждением, при необходимости — с третьим участником.
- Pooling на КТ2: после первого прогона блока A, до выбора конфигураций, просматриваем документы из первых 10 результатов всех прогонов, которых нет в разметке; найденные пропуски добавляем в `relevant`. После этого разметку замораживаем.

### 10.4. Равномерность

- По 3 запроса на каждую из 8 тем; поле `topic` — подкласс темы, для которой написан запрос.
- Тетрадка показывает распределение запросов по `topic` и документов корпуса по подклассу первого кода МПК (ожидаем ~25 на тему).

### 10.5. Формат

JSONL, UTF-8, одна запись на строку. Реальный файл — `benchmark/queries.jsonl` (КТ2); пример формата — `benchmark/queries.example.jsonl`:

```json
{"id": "Q-001", "query": "Хочу, чтобы огород поливался сам, когда земля пересыхает, и не поливался перед дождём", "relevant": ["DEMO-001", "DEMO-002", "DEMO-003"], "topic": "A01G"}
```

| Поле | Тип | Правило |
|---|---|---|
| `id` | string | `Q-001`, `Q-002`, …, уникальный |
| `query` | string | запрос своими словами, не меньше 3 слов |
| `relevant` | string[] | id документов корпуса, не меньше 3, без повторов |
| `topic` | string | подкласс МПК темы, например `A01G` |

В примере корпус из 3 демо-записей, поэтому релевантны все три.

### 10.6. Сроки

| Когда | Что |
|---|---|
| КТ1 (2026-10-07) | формат записи и benchmark, демо-данные, этот план, тетрадка с проверкой формата |

## 11. Ограничения подхода

- **Лексический разрыв.** BM25 учитывает только совпавшие термины и не знает синонимов. «Земля пересохла» и «влажность почвы» — разные леммы (`земля`, `пересохнуть` против `влажность`, `почва`), общих терминов нет. На демо-данных пример Q-001 («…огород поливался сам, когда земля пересыхает…») после предобработки совпадает с рефератами только по лемме `дождь` (DEMO-002), а Q-002 — только по `вода` (DEMO-001, DEMO-002), хотя по смыслу релевантны все три записи. Поэтому запросы benchmark пишутся своими словами: они должны показывать этот разрыв, а не прятать его.
- Лемматизация не объединяет однокоренные слова и видовые пары: «пересохла» → `пересохнуть`, «пересыхает» → `пересыхать`; `влага` ≠ `влажность`; `полив` ≠ `поливать`.
- Неоднозначность `parse()[0]`: «полив» → `полить` (раздел 4.4).
- Патентный стоп-список может удалить значимое слово запроса: «включать (воду)».
- Score не сравним между запросами, поэтому порог MIN_SCORE груб (раздел 7).

Что можно попробовать позже (после КТ2, вне основной сетки):

- небольшой словарь синонимов предметной области для расширения запроса (`земля` → `почва`, `пересохнуть` → `влажность`);
- псевдорелевантная обратная связь: добавить к запросу частые термины первых 3 документов и искать повторно;
- переформулировать запрос локальной LLM «языком патентов» перед BM25;
- правило выбора разбора: суммировать score по лемме и при равенстве предпочитать существительное — это исправит «полив»;
- векторный поиск по эмбеддингам вместе с BM25 — только в собственной реализации и после согласования с преподавателем.

## 12. Запреты из методички

- Поисковый индекс и BM25 — только собственная реализация. Запрещены rank_bm25, Whoosh, Elasticsearch, sklearn TfidfVectorizer в роли поиска и любые готовые поисковые индексы.
- Для лемматизации разрешён pymorphy3; выбор обоснован в разделе 4.4.
- Benchmark: запросы своими словами, равномерно по корпусу, не менее 3 релевантных документов на запрос; метрики Recall@k и MRR.
- Стек: Python 3.11+, FastAPI; фронтенд React + Vite + Tailwind; LLM через Ollama (OpenAI-совместимый API), модель задаётся в `.env`; тетрадки — marimo.
- Реальные номера патентов не выдумываем. Демо-данные: id вида `DEMO-001` и явная пометка «демонстрационные данные»; формат реального номера — только шаблоном `RU<номер><код вида>`, например `RU<7 цифр>C1`.
- На КТ1 работающий поиск не нужен: `app/search/` — только заготовки с докстрингами и `NotImplementedError`.
