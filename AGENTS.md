# AGENTS.md — правила работы с репозиторием

Правила обязательны для ИИ-агентов (Claude Code и других, которые читают `AGENTS.md`) и для участников команды. Claude Code читает `CLAUDE.md`, а тот подключает этот файл строкой `@AGENTS.md`; правила хранятся только здесь. Агент работает от имени участника, который его запустил, и только в его зоне (раздел 3). Если правило мешает задаче, его не обходят, а сообщают об этом владельцу зоны.

## 1. Порядок любого изменения

1. **Прочитать спецификацию** в `spec/` по таблице ниже — до изменения кода. Если код и спецификация расходятся, выяснить у владельца документа, что из них верно; не выбирать молча.
2. **Изменить код** в своей зоне.
3. **Обновить спецификацию в том же коммите**, если изменилось описанное в ней: поведение, формат данных, контракт API, параметры поиска, тексты интерфейса. Рефакторинг без изменения поведения спецификацию не меняет.
4. **Запустить тесты и benchmark** (раздел 5).
5. **Обновить `CHANGE_HISTORY.md`**: новая запись сверху, дата `ГГГГ-ММ-ДД`, кто и что сделал.
6. **Пройти чек-лист** «Готово к коммиту» (раздел 9).

| Область изменения | Прочитать до изменения | Обновить в том же коммите |

| Предобработка, индекс, BM25 — `app/search/` | `spec/tech/rag.md` | `spec/tech/rag.md` |

## 2. Жёсткие ограничения (из методички)

Нарушать нельзя, в том числе «временно» или «для проверки».

1. Поисковый индекс и BM25 — только собственная реализация. Запрещены `rank_bm25`, Whoosh, Elasticsearch, `sklearn` `TfidfVectorizer` в роли поиска и любые готовые поисковые индексы.
2. Для лемматизации разрешён `pymorphy3`; выбор обосновывается в `spec/tech/rag.md`.
3. Benchmark: запросы своими словами, равномерно по корпусу, не менее 3 релевантных документов на запрос; метрики Recall@k и MRR.
4. Стек: Python 3.11+, FastAPI; фронтенд React + Vite + Tailwind; LLM через Ollama (OpenAI-совместимый API), модель задаётся в `.env`; тетрадки — marimo.
5. Не выдумывать реальные номера патентов. Демо-данные: id вида `DEMO-001` и явная пометка «демонстрационные данные». Никаких номеров с конкретными цифрами, даже «для примера»; формат реального номера описывается только шаблоном `RU<номер><код вида>`, например `RU<7 цифр>C1`.
6. Работающий поиск на КТ1 не нужен: `app/search/` содержит только заготовки с докстрингами и `NotImplementedError`. Реализация BM25 — к КТ2.

Связанные правила проекта:

- Данные пользователя не уходят в облако: LLM работает локально через Ollama; провайдер `openai_compatible` — только с сервером на своём компьютере (LM Studio, llama.cpp server, vLLM).
- Пояснение LLM — первичный поиск аналогов, а не юридическое заключение. Дисклеймер в конце `answer` добавляет API, а не модель.
- Новые зависимости — только по согласованию: Python (`requirements.txt`) — с Колей, фронтенд (`frontend/package.json`) — с Никой.

## 3. Зоны ответственности

| Участник | Роль | Зона |
|---|---|---|
| Бобур | BM25 и RAG | `data/`, `app/search/`, `benchmark/`, `spec/tech/rag.md`, `app/llm/prompts.py` |
| Коля | Интеграция (бэкенд) | `app/api/`, `app/llm/client.py`, `tests/`, `spec/tech/architecture.md`, общие файлы в корне (`README.md`, `AGENTS.md`, `CLAUDE.md`, `CHANGE_HISTORY.md`, `.gitignore`, `requirements.txt`, `.env.example`, `pytest.ini`), `app/__init__.py`, `app/llm/__init__.py` |
| Ника | Продукт и интерфейс | `spec/product/`, `frontend/` |

- Каждый работает в своей зоне. Изменение в чужой зоне — только по согласованию с владельцем: предложить правку (сообщение в чате команды, issue или pull request), владелец принимает её или вносит сам.
- ИИ-агент меняет файлы только в зоне участника, который его запустил. Если задача требует правки в чужой зоне, агент останавливается и описывает нужное изменение, а не вносит его.
- `CHANGE_HISTORY.md` — общий журнал: каждый добавляет свои записи и не правит чужие.
- Тесты своего модуля (например, поиска) добавляются в `tests/` по согласованию с Колей.
- `AGENTS.md` меняется по согласованию всей команды.
- В `README.md` раздел «Запуск» стоит между маркерами `<!-- run:start -->` и `<!-- run:end -->`; маркеры не удалять.

## 4. Изменение контракта API

Контракт — запросы и ответы `GET /health` и `POST /search`: поля, типы, правила проверки, формат `answer`. Он описан в `spec/tech/architecture.md`, и на него опираются бэкенд, фронтенд-мок и тесты. Порядок изменения:

1. Согласовать изменение с Колей (владелец контракта) и Никой (фронтенд); если затронуты поиск или формат `answer` — и с Бобуром.
2. Сначала `spec/tech/architecture.md`: таблицы запроса и ответа, правила проверки, JSON-пример ответа.
3. Бэкенд: `app/api/schemas.py`, `app/api/stub.py`, `app/api/main.py`.
4. Фронтенд: типы и `searchPatents` в `frontend/src/api/`, мок `frontend/src/mock/search.json`.
5. Тесты: `tests/test_api.py` (он же сверяет мок фронтенда с контрактом).
6. `pytest` и `npm run build` проходят; в `CHANGE_HISTORY.md` — запись «изменён контракт API: что было → что стало».

Шаги 2–5 выполняются согласованно: одним коммитом (если владельцы поручили всё одному человеку) или подряд в оговорённом порядке, без других изменений между ними. Менять контракт «по пути» — только в коде, только в моке или только в тестах — нельзя.

## 5. Тесты и benchmark

Команды выполняются из корня репозитория в виртуальном окружении Python 3.11+ с зависимостями из `requirements.txt` (см. раздел «Запуск» в `README.md`):

```bash
pytest
python benchmark/experiments.py
marimo edit benchmark/experiments.py
cd frontend && npm run build
```

- `pytest` — тесты; запускать перед каждым коммитом с кодом.
- `python benchmark/experiments.py` — тетрадка benchmark как обычный скрипт; `marimo edit …` — та же тетрадка интерактивно, в браузере.
- `npm run build` в `frontend/` — при изменениях во `frontend/`: сборка и проверка типов.
- Тесты не требуют сети и Ollama: LLM в тестах заменяется провайдером `stub` или `httpx.MockTransport`. Новые тесты пишутся так же.
- На КТ1 тетрадка только проверяет формат benchmark (`benchmark/queries.example.jsonl`) и показывает план экспериментов. Метрики Recall@5, Recall@10 и MRR появятся после реализации BM25.
- После реализации BM25 изменения в `app/search/`, `data/` и `benchmark/` не должны ухудшать метрики без объяснения. Главная метрика — Recall@5 (см. `spec/tech/rag.md`). Значения до и после записываются в `CHANGE_HISTORY.md`, смена выбранной конфигурации — в `spec/tech/rag.md`.
- Если тест падает, сначала выяснить, что неверно — код или спецификация. Ожидаемые значения в тестах под код не подгоняются.

## 6. Секреты и `.env`

- `.env` не коммитится (он в `.gitignore`). Настройки LLM задаются в `.env`; образец без секретов — `.env.example`. Новая переменная окружения добавляется в `.env.example` и `spec/tech/architecture.md` в том же коммите.
- Ключи, токены и пароли не записываются в код, тесты, тетрадки, документы и сообщения коммитов. Локальному Ollama ключ не нужен: `LLM_API_KEY=ollama` — заполнитель.
- `frontend/.env.api` коммитится: в нём только `VITE_API_MODE=api`. Всё, что начинается с `VITE_`, попадает в код страницы и видно в браузере, поэтому секреты в такие переменные не записывают. Локальные переопределения — в файлах `*.local`, они не коммитятся.
- Если секрет попал в коммит, сообщить команде и заменить (отозвать) ключ: удаление файла следующим коммитом не помогает — файл остаётся в истории git.

## 7. Демонстрационные данные

- Демо-записи имеют id `DEMO-001`, `DEMO-002`, … и поле `source` со значением `"демонстрационные данные"`. Их тексты придуманы и не описывают реальные патенты.
- Демо-записи лежат в `data/sample/patents.jsonl`; их копии — в заглушке бэкенда `app/api/stub.py` и в моке фронтенда `frontend/src/mock/search.json`. Менять их нужно согласованно во всех трёх местах и в тестах.
- Пометка обязательна везде, где демо-записи видит пользователь: в интерфейсе — плашка «Демонстрационные данные: …» (по префиксу `DEMO-` в id), в ответе API — вводный абзац `answer`.
- Демо-записи не смешиваются с реальным корпусом `data/corpus/patents.jsonl`.
- Реальные записи (с КТ2) берутся только из открытых реестров ФИПС: номер, название, реферат, МПК и год — как опубликованы, в `source` — адрес страницы документа. В тестах, примерах, промптах и документах — только id вида `DEMO-001` или шаблон `RU<номер><код вида>`.

## 8. Дополнительно для ИИ-агентов

- Не выполнять `git commit`, `git push` и операции, переписывающие историю (`git rebase`, `git reset --hard`, `git push --force`), без явной просьбы человека.
- Не реализовывать то, что на текущем этапе намеренно оставлено заготовкой (на КТ1 — поиск в `app/search/` и вызов LLM из `POST /search`), если об этом прямо не попросили.
- Не выдумывать номера патентов, рефераты, метрики и результаты экспериментов. Цифры качества берутся только из прогона тетрадки benchmark.
- Документы, комментарии и докстринги — на русском; имена в коде — на английском. Ссылки на файлы — относительные пути от корня репозитория.
- В конце работы сообщить человеку: что изменено, какие проверки запущены и с каким результатом, что не проверено и почему.

## 9. Чек-лист «Готово к коммиту»

- [ ] Изменения — в своей зоне или согласованы с владельцем (раздел 3).
- [ ] Нужная спецификация в `spec/` прочитана и обновлена в этом же коммите.
- [ ] Жёсткие ограничения (раздел 2) не нарушены: нет готовых поисковых библиотек, нет выдуманных номеров патентов.
- [ ] Контракт API не изменён или изменён по протоколу (раздел 4).
- [ ] `pytest` проходит.
- [ ] `python benchmark/experiments.py` выполняется без ошибок; после реализации BM25 метрики не хуже прежних или причина записана.
- [ ] При изменениях во `frontend/` — `npm run build` без ошибок.
- [ ] В `CHANGE_HISTORY.md` добавлена запись.
- [ ] В `git status` нет `.env`, секретов, `node_modules/`, `.venv/`, `__pycache__/`, `dist/`, `__marimo__/`.
- [ ] Сообщение коммита — `тип(область): что сделано` по-русски, область можно опустить (`chore: …`); типы `feat`, `fix`, `docs`, `test`, `refactor`, `chore`. Пример: `docs(rag): спецификация поиска BM25 и плана экспериментов (КТ1)`.
