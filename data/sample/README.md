# Данные: формат записи патента, демо-данные и корпус

> **Демонстрационные данные.** `data/sample/patents.jsonl` содержит 3 записи, составленные вручную для прототипа. Это не реальные патенты: `DEMO-001`, `DEMO-002`, `DEMO-003` — не номера патентов, у всех трёх записей `source` = `"демонстрационные данные"`. Реальный корпус — `data/corpus/patents.jsonl` (раздел «Реальный корпус»); демо-записи в него не входят.

Как корпус используется в поиске (документ = название + реферат, предобработка, BM25) — в [spec/tech/rag.md](../../spec/tech/rag.md).

## Файлы

| Путь | Что | Когда |
|---|---|---|
| `data/sample/patents.jsonl` | 3 демо-записи (полив и датчики влажности почвы): прототип, тесты, пример benchmark | КТ1 |
| `data/corpus/patents.jsonl` | реальный корпус: 200 рефератов патентов РФ на изобретения, 8 тем | КТ2 |
| `data/corpus/groups.json` | состав корпуса: темы, группы близких патентов, поисковые запросы групп и выбранные номера | КТ2 |
| `data/tools/collect_corpus.py` | сбор корпуса через API поисковой платформы Роспатента | КТ2 |

## Формат записи

Файл JSONL: кодировка UTF-8, одна запись — одна строка, без запятых между строками и без общего массива `[...]`. Запись DEMO-003 (в файле — одной строкой; здесь разбита для читаемости):

```json
{
  "id": "DEMO-003",
  "title": "Беспроводной датчик влажности почвы с автономным питанием",
  "abstract": "Изобретение относится к измерительной технике, а именно к средствам контроля влажности почвы. Беспроводной датчик влажности почвы, содержащий корпус с погружным зондом, ёмкостный измерительный элемент, микроконтроллер и радиомодуль, передающий результаты измерений на базовую станцию, отличающийся тем, что питание осуществляется от аккумулятора, заряжаемого солнечной панелью, установленной на верхней части корпуса, а микроконтроллер переводит датчик в режим пониженного энергопотребления между измерениями и увеличивает интервал измерений при стабильной влажности почвы. Технический результат — увеличение срока автономной работы датчика без обслуживания.",
  "ipc": ["G01N 33/24", "G01N 27/22", "H04W 4/38"],
  "year": 2023,
  "source": "демонстрационные данные"
}
```

Все шесть полей обязательны, других полей нет.

| Поле | Тип | Откуда в документе ФИПС (код INID) | Правило |
|---|---|---|---|
| `id` | string | (19) RU + (11) номер + (13) код вида | `RU<номер><код вида>` без пробелов, например `RU<7 цифр>C1`; у демо-записей — `DEMO-001` |
| `title` | string | (54) название | одной строкой |
| `abstract` | string | (57) реферат | весь текст реферата одной строкой |
| `ipc` | string[], непустой | (51) МПК | каждый код — строка вида `"A01G 25/16"`; несколько кодов — список, первым — основной код |
| `year` | integer | (45) дата публикации | только год, числом: `2021` |
| `source` | string | адрес страницы документа | URL страницы в открытом реестре ФИПС; у демо-записей — `"демонстрационные данные"` |

Поля (21) и (22) — номер и дата подачи заявки — не сохраняем.

### Правила нормализации

1. **МПК без версии.** В документе код записан с версией редакции МПК: `A01G 25/16 (2006.01)` → в файл пишем `"A01G 25/16"`. Буквы — латинские (не кириллические А, В, С, Е, Н, К, М, О, Р, Т, Х), между подклассом и группой — один пробел.
2. **Несколько кодов — список.** Первым — основной код, то есть первый код (51) документа: по нему запись относится к теме. Остальные коды — в том порядке, в котором их отдаёт API Роспатента (по возрастанию); на странице ФИПС дополнительные коды могут стоять в другом порядке, набор кодов тот же. Если на странице есть коды СПК (52), их не берём — только (51).
3. **Год — из (45)**, только год, целым числом, без кавычек.
4. **Реферат — одной строкой.** Переносы строк и повторяющиеся пробелы заменяем одним пробелом. Если реферат заканчивается служебной припиской вида «2 з.п. ф-лы, 3 ил.» (число пунктов формулы, иллюстраций, таблиц, примеров), её не копируем.
5. **Название** — как в документе, одной строкой; если оно набрано прописными буквами, приводим к обычному написанию: заглавная только первая буква, аббревиатуры остаются прописными.
6. **UTF-8**; «ё» оставляем как в источнике — её обрабатывает предобработка.
7. **Одна запись — одна строка JSONL**, файл заканчивается переводом строки.

## Реальный корпус

### Источник

Корпус собран скриптом `data/tools/collect_corpus.py` через API ИС «Поисковая платформа» Роспатента (https://searchplatform.rospatent.gov.ru/patsearch/v0.2/), массив `ru_since_1994` — патентные документы России с 1994 года. Это официальный программный доступ к тем же публикациям Роспатента, что в открытых реестрах ФИПС.

- **Ключ API** (JWT) выдаётся зарегистрированному пользователю платформы в разделе «Разработчикам». Скрипт читает его только из переменной окружения `ROSPATENT_TOKEN`; в файлы, вывод и git ключ не попадает.
- **Кеш.** Сырые ответы API скрипт сохраняет в каталог `../kt2-raw/` рядом с репозиторием (вне git; другой каталог — опция `--raw-dir`). Повторный запуск берёт ответы из кеша и в сеть не ходит; ключ нужен, только если ответа в кеше нет.
- **Пауза** между запросами к API — не меньше 1 с (по умолчанию 1,2 с). При сетевом сбое или ответе 502–504 скрипт повторяет запрос до 3 раз; при ответе 429 (ограничение числа запросов) останавливается.
- **Страницы ФИПС скрипт не открывает:** robots.txt открытого реестра ФИПС запрещает роботам раздел `/registers-doc-view/`. Адрес страницы документа в поле `source` строится по шаблону. Корпус сверен автоматически с двумя ответами API (раздел «Сверка корпуса»).

### Отбор записей

1. Тема — подкласс МПК (таблица «Распределение тем»). Внутри темы — 3 группы близких патентов по 8–9 записей: одно назначение и сходный способ (таблица «Группы внутри тем»), чтобы у каждого запроса benchmark нашлось не меньше 3 релевантных.
2. Кандидаты группы — выдача API на смысловой запрос группы (поле `query` в `groups.json`, параметр `qn`) с фильтрами: страна RU, вид C1 или C2, группа МПК (`classification.ipc_group`). В малых группах смысловой запрос находит единицы документов, поэтому там кандидаты — все документы группы или подгруппы (поле `q`): в B62K (например, `IC=B62K15`), в F25D — оттаивание (`IC=F25D21`) и естественный холод (`IC=F25D1`), в H02J — заряд от солнечных батарей (`IC=H02J7/35`).
3. Правила записи — скрипт проверяет их при сборке и не записывает корпус, если хоть одно нарушено:
   - патент РФ на изобретение из реестра RUPAT: страна публикации RU, вид C1 или C2;
   - первый код МПК (51) — из подкласса темы: так каждый патент попадает ровно в одну тему;
   - реферат непустой и передаётся текстом без потерь: без формул-картинок, MathML и таблиц внутри текста. Копия реферата из базы DOCDB (`dataFormat="docdba"` в ответе API) принимается, только если кончается припиской «… ил.», «… ф-лы»: без приписки длинный реферат DOCDB бывает обрезан на полуслове (найдено сверкой с ФИПС). При сборке реферат такой записи всё равно берётся из исходного XML документа (раздел «Поля записи»);
   - все коды МПК полные: раздел, класс, подкласс, группа и подгруппа;
   - номер не повторяется.
4. Номера в группы выбраны вручную по названию и реферату кандидатов: то же назначение и сходный способ. Ничего не дописано: все поля — как в публикации, с нормализацией по правилам выше.

### Поля записи

API отдаёт документ двумя способами: `GET /docs/<id>` (JSON) и XML документа в формате ST96 (медиаметод, адрес — поле `ex_xml` ответа `/docs`).

| Поле | Откуда | Преобразование |
|---|---|---|
| `id` | `/docs`: `common.publishing_office`, `common.document_number`, `common.kind` | `RU` + номер без ведущих нулей + код вида |
| `title` | XML: `InventionTitle` на русском (в `/docs` — `biblio.ru.title`: у части названий там пропущены пробелы на месте переноса строки) | правило 5: если всё набрано прописными — заглавная только первая буква; слово остаётся прописным (или в написании вроде «pH»), если так же написано в реферате или стоит в кавычках |
| `abstract` | `/docs`: `abstract.ru`, если он в исходном виде (`dataFormat="original"`); иначе — исходный реферат из XML: в копии DOCDB (`dataFormat="docdba"`) длинные рефераты обрезаны, а подстрочные индексы и часть пробелов потеряны | текст без номера абзаца «[N]» и без рисунка после текста; одной строкой; без приписки «… з.п. ф-лы, … ил.» (правило 4) |
| `ipc` | `common.classification.ipc[].fullname`, например `A01G25/16` | `A01G 25/16`; первым — основной код (правило 2) |
| `year` | `common.publication_date`, например `2014.07.20` | год |
| `source` | — | `https://new.fips.ru/registers-doc-view/fips_servlet?DB=RUPAT&DocNumber=<номер>&TypeFile=html` |

### Повторить сбор

Из корня репозитория, в окружении из раздела «Запуск» `README.md`; на macOS и Linux — `python3` вместо `python`, если окружение не активировано. Если в кеше `../kt2-raw/` ответов нет, сначала задайте в этом же терминале переменную окружения `ROSPATENT_TOKEN` с ключом API (macOS, Linux: `export ROSPATENT_TOKEN=…`; Windows PowerShell: `$env:ROSPATENT_TOKEN="…"`, вместо многоточия — ключ).

```bash
python data/tools/collect_corpus.py selftest
python data/tools/collect_corpus.py search
python data/tools/collect_corpus.py build
python data/tools/collect_corpus.py verify
python data/tools/collect_corpus.py spotcheck
```

- `selftest` — проверка нормализации на встроенных примерах, без сети.
- `search` — кандидаты по запросам групп из `groups.json`: выдача API и рефераты первых кандидатов; результат — в `../kt2-raw/candidates/` для ручного отбора номеров.
- `build` — `data/corpus/patents.jsonl` по номерам из `groups.json`: проверяет правила записи и печатает отчёт — число записей по темам и группам, длины рефератов, годы, названия, приведённые из прописных.
- `verify` — сверка каждой записи корпуса с двумя ответами API: `GET /docs` и XML документа (раздел «Сверка корпуса»); полный отчёт — `../kt2-raw/verify_report.json`.
- `spotcheck` — по 2 записи на тему: адрес страницы ФИПС и поля для необязательной ручной сверки.

### Сверка корпуса

**Автоматическая сверка корпуса с двумя ответами API Роспатента** — `GET /docs` и XML документа — по всем 200 записям (команда `verify`). Сравниваются номер, вид, название (без учёта регистра букв — оно приведено по правилу 5), коды МПК (набор, первый код, порядок), год публикации и реферат.

| Поле | корпус = `/docs` | корпус = XML | `/docs` = XML |
|---|---|---|---|
| номер | 200 из 200 | 200 из 200 | 200 из 200 |
| вид | 200 из 200 | 200 из 200 | 200 из 200 |
| название | 197 из 200 | 200 из 200 | 197 из 200 |
| МПК: набор, первый код, порядок | 200 из 200 | 200 из 200 | 200 из 200 |
| год | 200 из 200 | 200 из 200 | 200 из 200 |
| реферат | 192 из 200 | 198 из 200 | 190 из 200 |

Расхождения и как решены:

- **Название, 3 записи:** в `/docs` пропущен пробел на месте переноса строки («ВОДИ», «ИПРОИЗВОДСТВЕННЫХ», «РАБОТЫЭТОГО»), в XML — верно. Исправлено по XML: название теперь берётся из XML документа.
- **Реферат, 8 записей:** `/docs` отдаёт копию реферата из базы DOCDB — 1 реферат обрезан на полуслове, в 7 потеряны подстрочные индексы и пробелы (CO2 → CO, СН4 → СН, O2 → O, M1 → M). Реферат этих записей в корпусе — из исходного XML.
- **Реферат, 2 записи:** в XML перед надстрочным знаком стоит тонкий пробел (U+200A): «NH4 +», «см 3» вместо «NH4+», «см3». Текст тот же; оставлено как в `/docs`.

**Выборочно со страницами ФИПС** сверены 4 документа подкласса A01G на этапах 0–1 (страницы открыты разово, вручную; в итоговый корпус эти документы не вошли): номер, вид, название и год совпали у всех четырёх; набор кодов МПК — у всех четырёх, а порядок дополнительных кодов отличается у двух (правило 2); реферат `/docs` у одного документа обрезан (копия DOCDB), исходный реферат из XML совпал с ФИПС дословно у двух проверенных.

**Необязательная ручная проверка.** Команда `spotcheck` выбирает по 2 записи на тему (16 записей; выбор детерминированный — по SHA-256 номера) и печатает адрес страницы ФИПС и поля записи. Страницу открывают в браузере и сверяют: (11) номер и (13) код вида — с `id`; (54) название — с `title` без учёта регистра; (51) МПК — первый код и набор кодов с `ipc` (порядок остальных может отличаться); (45) год — с `year`; (57) реферат — начало и конец с `abstract`.

## Контроль дублей

- `id` уникален во всём корпусе: `build` останавливается, если номер повторяется в `groups.json`.
- Патент с кодами двух тем (как DEMO-001: A01G и G01N) попадает в тему по первому коду (51): так он оказывается ровно в одной теме.
- Берём только патенты на изобретения (вид C1, C2), не публикации заявок (вид A).
- Команда проверки ниже показывает повторяющиеся `id`.

## Чек-лист записи

Для записей корпуса пункты проверяют `build` и `verify` (раздел «Сверка корпуса»); ручная сверка с ФИПС — необязательна.

- [ ] `id` = `RU` + номер (11) + код вида (13), без пробелов; номер совпадает с `DocNumber` в `source`
- [ ] `title` — название (54), одной строкой
- [ ] `abstract` — весь реферат (57), одной строкой, без переносов и без приписки «… з.п. ф-лы, … ил.»
- [ ] `ipc` — все коды (51) списком, латиница, вид `A01G 25/16`, без версии `(2006.01)`; первым — основной код
- [ ] `year` — год из (45), целым числом
- [ ] `source` открывается и ведёт на этот же документ
- [ ] такого `id` ещё нет в корпусе
- [ ] первый код из `ipc` — подкласса темы
- [ ] файл проходит команду проверки

## Команда проверки файла

Из корня репозитория (на macOS и Linux — `python3` вместо `python`; путь к файлу — последний аргумент):

```bash
python -c "import json,re,sys; rows=[json.loads(s) for s in open(sys.argv[1],encoding='utf-8') if s.strip()]; ids=[r.get('id') for r in rows]; K={'id','title','abstract','ipc','year','source'}; ok=lambda r: set(r)==K and re.fullmatch(r'RU[0-9]+[A-Z][0-9]?|DEMO-[0-9]{3}',str(r['id'])) and str(r['title']).strip() and str(r['abstract']).strip() and '\n' not in r['abstract'] and isinstance(r['ipc'],list) and r['ipc'] and all(re.fullmatch(r'[A-H][0-9]{2}[A-Z] [0-9]{1,4}/[0-9]{2,6}',str(c)) for c in r['ipc']) and type(r['year']) is int and str(r['source']).strip(); print('записей:',len(rows),'| дубли id:',sorted({i for i in ids if ids.count(i)>1}) or 'нет','| записи с ошибками:',[r.get('id') for r in rows if not ok(r)] or 'нет')" data/sample/patents.jsonl
```

Для демо-файла вывод: `записей: 3 | дубли id: нет | записи с ошибками: нет`; с путём `data/corpus/patents.jsonl` — `записей: 200 | дубли id: нет | записи с ошибками: нет`. Команда проверяет набор полей, формат `id` и кодов МПК (латиница, без версии), тип `year` и отсутствие переносов в реферате; строка с ошибкой JSON остановит команду с сообщением `json.decoder.JSONDecodeError`. Полную проверку benchmark (релевантные документы есть в корпусе, распределение по темам) делает тетрадка `benchmark/experiments.py`.

## Где хранится реальный корпус

- Корпус — один файл `data/corpus/patents.jsonl`; API и тетрадка benchmark читают только его. Файл собирает команда `build` из номеров в `data/corpus/groups.json`, вручную его не правят: чтобы добавить или заменить запись, меняют номера в `groups.json` и пересобирают корпус.
- Демо-записи в реальный корпус не копируем: `data/sample/` остаётся для прототипа и тестов.
