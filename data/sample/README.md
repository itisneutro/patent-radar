# Данные: формат записи патента и ручной сбор рефератов

> **Демонстрационные данные.** `data/sample/patents.jsonl` содержит 3 записи, составленные вручную для прототипа. Это не реальные патенты: `DEMO-001`, `DEMO-002`, `DEMO-003` — не номера патентов, у всех трёх записей `source` = `"демонстрационные данные"`. Реальный корпус появится к КТ2 в `data/corpus/patents.jsonl`.

Как корпус используется в поиске (документ = название + реферат, предобработка, BM25) — в [spec/tech/rag.md](../../spec/tech/rag.md).

## Файлы

| Путь | Что | Когда |
|---|---|---|
| `data/sample/patents.jsonl` | 3 демо-записи (полив и датчики влажности почвы): прототип, заглушка API, тетрадка benchmark | КТ1 |
| `data/corpus/patents.jsonl` | реальный корпус: ~200 рефератов патентов РФ на изобретения, 8 тем × ~25 | КТ2 |

## Формат записи

Файл JSONL: кодировка UTF-8, одна запись — одна строка, без запятых между строками и без общего массива `[...]`. Запись DEMO-003 (в файле — одной строкой; здесь разбита для читаемости):

```json
{
  "id": "DEMO-003",
  "title": "Беспроводной датчик влажности почвы с автономным питанием",
  "abstract": "Изобретение относится к измерительной технике, а именно к средствам контроля влажности почвы. Беспроводной датчик влажности почвы, содержащий корпус с погружным зондом, ёмкостный измерительный элемент, микроконтроллер и радиомодуль, передающий результаты измерений на базовую станцию, отличающийся тем, что питание осуществляется от аккумулятора, заряжаемого солнечной панелью, установленной на верхней части корпуса, а микроконтроллер переводит датчик в режим пониженного энергопотребления между измерениями и увеличивает интервал измерений при стабильной влажности почвы. Технический результат — увеличение срока автономной работы датчика без обслуживания.",
  "ipc": ["G01N 33/24", "G01N 27/22", "H04W 4/38"],
  "year": 2023,
  "source": "демонстрационные данные"
}
```

Все шесть полей обязательны, других полей нет.

| Поле | Тип | Откуда в документе ФИПС (код INID) | Правило |
|---|---|---|---|
| `id` | string | (19) RU + (11) номер + (13) код вида | `RU<номер><код вида>` без пробелов, например `RU<7 цифр>C1`; у демо-записей — `DEMO-001` |
| `title` | string | (54) название | одной строкой |
| `abstract` | string | (57) реферат | весь текст реферата одной строкой |
| `ipc` | string[], непустой | (51) МПК | каждый код — строка вида `"A01G 25/16"`; несколько кодов — список |
| `year` | integer | (45) дата публикации | только год, числом: `2021` |
| `source` | string | адрес страницы документа | URL страницы в открытом реестре ФИПС; у демо-записей — `"демонстрационные данные"` |

Поля (21) и (22) — номер и дата подачи заявки — не сохраняем.

### Правила нормализации

1. **МПК без версии.** В документе код записан с версией редакции МПК: `A01G 25/16 (2006.01)` → в файл пишем `"A01G 25/16"`. Буквы — латинские (не кириллические А, В, С, Е, Н, К, М, О, Р, Т, Х), между подклассом и группой — один пробел.
2. **Несколько кодов — список** в порядке документа: `["A01G 25/16", "G01N 27/22"]`. Если на странице есть коды СПК (52), их не берём — только (51).
3. **Год — из (45)**, только год, целым числом, без кавычек.
4. **Реферат — одной строкой.** Переносы строк и повторяющиеся пробелы заменяем одним пробелом. Если реферат заканчивается служебной припиской вида «2 з.п. ф-лы, 3 ил.» (число зависимых пунктов формулы и иллюстраций), её не копируем.
5. **Название** — как в документе, одной строкой; если оно набрано прописными буквами, приводим к обычному написанию: заглавная только первая буква, аббревиатуры остаются прописными.
6. **UTF-8**; «ё» оставляем как в источнике — её обрабатывает предобработка.
7. **Одна запись — одна строка JSONL**, файл заканчивается переводом строки.

## Как собрать реферат вручную из открытых реестров ФИПС

1. Открыть https://new.fips.ru/registers-web/ → раздел «Изобретения» → «Реестр изобретений» (база RUPAT). Нужен именно реестр патентов, а не «Реестр заявок на выдачу патента на изобретение»: у заявки и выданного по ней патента почти одинаковый реферат, это был бы дубль.
2. Найти документ. Открытый реестр выдаёт документ по номеру (номер вводится в окошко запроса); поиска по словам и кодам МПК в нём нет. Поэтому номера патентов своей темы сначала находим поиском по коду МПК темы и ключевым словам — в информационно-поисковой системе ФИПС (ссылка «Информационно-поисковая система» есть на той же странице) или в другом патентном поисковике — и затем открываем каждый документ в реестре. Страница документа:

   ```text
   https://new.fips.ru/registers-doc-view/fips_servlet?DB=RUPAT&DocNumber=<номер>&TypeFile=html
   ```

   `<номер>` — номер патента из поля (11), только цифры, без «RU» и кода вида.
3. Проверить на странице, что это патент РФ на изобретение — (19) RU, код вида (13) обычно C1 или C2, — и что хотя бы один код (51) относится к подклассу вашей темы.
4. Скопировать поля:
   - (11) и (13) → `id` = `RU` + номер + код вида;
   - (54) → `title`;
   - (57) → `abstract` (только текст реферата, без слова «Реферат» и без приписки «… з.п. ф-лы, … ил.»);
   - (51) → `ipc` (все коды, без версий);
   - (45) → `year` (год из даты публикации);
   - адрес страницы документа → `source`.
5. Добавить запись одной строкой в файл своей темы (раздел «Где хранить реальный корпус») и проверить её по чек-листу.

## Распределение тем

8 тем × ~25 рефератов; тема — подкласс МПК, все подклассы из разных разделов МПК. Внутри темы собираем 3 группы близких патентов по 8–9 рефератов, чтобы на каждый запрос benchmark нашлось не меньше 3 релевантных. Запросы к теме пишет участник, который её не собирал (подробнее — [spec/tech/rag.md](../../spec/tech/rag.md), раздел 10). Список предварительный: утверждаем вместе до начала сбора; при замене темы берём другой подкласс того же раздела и правим эту таблицу и rag.md.

| Тема | Подкласс МПК | Область | Собирает рефераты | Пишет запросы |
|---|---|---|---|---|
| 1 | A01G | садоводство, выращивание растений, полив | Бобур | Коля |
| 2 | B62K | велосипеды и самокаты | Бобур | Коля |
| 3 | C02F | очистка воды и сточных вод | Бобур | Коля |
| 4 | D06F | стирка, сушка и глажение белья | Коля | Ника |
| 5 | E06B | двери, окна, жалюзи, ворота | Коля | Ника |
| 6 | F25D | холодильники и морозильные камеры | Коля | Ника |
| 7 | G01N | исследование и анализ материалов, датчики их свойств | Ника | Бобур |
| 8 | H02J | электропитание, зарядка аккумуляторов | Ника | Бобур |

## Контроль дублей

- `id` уникален во всём корпусе. Перед добавлением записи проверяем, что этого номера ещё нет в файлах всех тем.
- Патент с кодами двух тем (как DEMO-001: A01G и G01N) записываем один раз — в тему, к которой он ближе по смыслу; вторая тема его не повторяет.
- Берём только патенты из «Реестра изобретений» (RUPAT), не публикации заявок (шаг 1 инструкции).
- После объединения файлов команда проверки ниже показывает повторяющиеся `id`.

## Чек-лист записи

- [ ] `id` = `RU` + номер (11) + код вида (13), без пробелов; номер совпадает с `DocNumber` в `source`
- [ ] `title` — название (54), одной строкой
- [ ] `abstract` — весь реферат (57), одной строкой, без переносов и без приписки «… з.п. ф-лы, … ил.»
- [ ] `ipc` — все коды (51) списком, латиница, вид `A01G 25/16`, без версии `(2006.01)`
- [ ] `year` — год из (45), целым числом
- [ ] `source` открывается и ведёт на этот же документ
- [ ] такого `id` ещё нет в корпусе
- [ ] хотя бы один код из `ipc` — подкласса вашей темы
- [ ] файл проходит команду проверки

## Команда проверки файла

Из корня репозитория (на macOS и Linux — `python3` вместо `python`; путь к файлу — последний аргумент):

```bash
python -c "import json,re,sys; rows=[json.loads(s) for s in open(sys.argv[1],encoding='utf-8') if s.strip()]; ids=[r.get('id') for r in rows]; K={'id','title','abstract','ipc','year','source'}; ok=lambda r: set(r)==K and re.fullmatch(r'RU[0-9]+[A-Z][0-9]?|DEMO-[0-9]{3}',str(r['id'])) and str(r['title']).strip() and str(r['abstract']).strip() and '\n' not in r['abstract'] and isinstance(r['ipc'],list) and r['ipc'] and all(re.fullmatch(r'[A-H][0-9]{2}[A-Z] [0-9]{1,4}/[0-9]{2,6}',str(c)) for c in r['ipc']) and type(r['year']) is int and str(r['source']).strip(); print('записей:',len(rows),'| дубли id:',sorted({i for i in ids if ids.count(i)>1}) or 'нет','| записи с ошибками:',[r.get('id') for r in rows if not ok(r)] or 'нет')" data/sample/patents.jsonl
```

Для демо-файла вывод: `записей: 3 | дубли id: нет | записи с ошибками: нет`. Команда проверяет набор полей, формат `id` и кодов МПК (латиница, без версии), тип `year` и отсутствие переносов в реферате; строка с ошибкой JSON остановит команду с сообщением `json.decoder.JSONDecodeError`. Полную проверку benchmark (релевантные документы есть в корпусе, распределение по темам) делает тетрадка `benchmark/experiments.py`.

## Где хранить реальный корпус

- Во время сбора — отдельный файл на каждую тему: `data/corpus/<подкласс>.jsonl`, например `data/corpus/A01G.jsonl`. Так участники не правят один файл одновременно и не получают конфликтов в git.
- К КТ2 Бобур объединяет файлы тем в `data/corpus/patents.jsonl` командой ниже (тоже из корня репозитория), проверяет результат командой проверки с путём `data/corpus/patents.jsonl` и удаляет файлы тем. API и тетрадка benchmark читают только `data/corpus/patents.jsonl`.

  ```bash
  python -c "import glob,sys; rows=[s.strip() for f in sorted(glob.glob('data/corpus/[A-H][0-9][0-9][A-Z].jsonl')) for s in open(f,encoding='utf-8') if s.strip()]; rows or sys.exit('файлов тем data/corpus/<подкласс>.jsonl нет или они пустые — patents.jsonl не изменён'); open('data/corpus/patents.jsonl','w',encoding='utf-8').write('\n'.join(rows)+'\n'); print('объединено записей:',len(rows))"
  ```

  Команда собирает `patents.jsonl` заново только из файлов тем и перезаписывает его. Поэтому после удаления файлов тем её больше не запускают: новые записи добавляют прямо в `data/corpus/patents.jsonl`. Если файлов тем нет или в них нет записей, команда печатает сообщение об этом и завершается, а `patents.jsonl` не меняется.

- Демо-записи в реальный корпус не копируем: `data/sample/` остаётся для прототипа и тестов.
